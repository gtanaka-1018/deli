# 振込金額の記録と集計

更新日: 2026-09-15

## 振込だけをファイルから取り込む

設定の「データの保存・読込」から「振込だけを読み込む」を選ぶ。専用 JSON の日付・プラットフォーム・金額を確認し、件数と合計を確認して取り込む。通常の「ファイルから読み込む」は全体バックアップの復元である。

- 振込が未登録の日は追加する。売上・経費・稼働時間・資産・整備履歴などは保持する。
- 同日の既存振込がすべて未分類で、合計が一致する場合は分類を付ける。旧シートの `sourceData.transferAmount` も対象になる。
- 分類と金額がすでに一致する日は ID とメモを含めて保持し、再取り込みで二重登録しない。
- 金額や分類が異なる既存振込、読み取れない既存明細がある場合は、対象日を表示して全件の取り込みを中止する。一部だけ追加することはない。
- 未保存の入力があるときは、先に保存する。確認中に記録が変化した場合も再読み込みを求める。

専用ファイルの形式（架空の例）:

```json
{
  "format": "okumeter-payout-import",
  "version": 1,
  "entries": [
    { "date": "2026-09-01", "providerId": "uber", "amount": 1000, "memo": "振込日のルールで分類" }
  ]
}
```

`providerId` は `uber` / `rocket` / `demae`、金額は正の安全な整数とする。同日同社の重複や不正な明細はファイル全体を拒否する。分類はファイル作成時に確定し、アプリは日付から勝手に再分類しない。追加の `source` 情報は取込条件として実行しない。

### 互換性とロールバック

保存する日別 `payouts` の形式は従来と同じで、保存形式の版数は現行の `schemaVersion: 4` のままとする。取り込み直前の完全な状態を毎回「振込の取り込み直前」の復元ポイントへ保存し、保存が失敗したら反映しない。端末内の保存に失敗した場合も、画面上の記録を取り込み前へ戻す。

取り込みを取り消す場合は、設定の復元ポイントから「振込の取り込み直前」を選ぶ。復元はその時点の全記録を戻すため、その後に追加した記録がある場合は先にファイル保存する。コードを旧版へ戻す場合も、既存の `payouts` 対応版で明細は保持される。専用取込ファイルには `records` がないため、非対応版の全体バックアップ読み込みでは拒否される。

### 家計簿からの分類ルール

今回のファイル作成は、指定された曜日ルールに従う。火曜日を Uber、金曜日を Rocket Now とし、土日・国民の祝日・銀行休業日（12月31日、1月2日、1月3日）は翌営業日へ繰り越す。そのどちらにも該当しない日は出前館にする。同じセルに加算式がある場合も、ユーザーの指定に従って合計全額を1社へ分類する。複数の定期振込日が同じ営業日へ繰り越される場合は、自動配分せず確認する。

祝日・振替休日は [内閣府の国民の祝日](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html) の公式 CSV を用いる。添付の祝日シートには節分なども含まれるため、その全行を休業日として扱わない。これは今回の取り込みのために指定された分類であり、各社一般の振込規約を定義するものではない。元ファイル・分類結果・取り込み用 JSON は非公開の `data/` に置き、Git と公開サイトには含めない。

## 記録の意味

振込金額は、プラットフォームから実際に振り込まれた金額を記録する。振込日は日別記録の `date` とする。同日に複数のプラットフォームから入金があった場合や、同じプラットフォームから複数回入金があった場合は、振込をそれぞれ追加する。

振込額は売上とは別に集計する。売上・利益・税額の計算へ加算せず、純資産の残高も自動では変更しない。売上とその振込を二重に収入へ計上しないためである。振込日の集計なので、その期間に稼いだ売上と振込額が一致するとは限らない。

## データ形式と互換性

振込は `schemaVersion: 3` で導入し、既存の `records[日付]` に `payouts` 配列を追加した。現行版は整備履歴を含む `schemaVersion: 4` を使う。既存の売上・経費フィールドは引き続き利用する。

```json
{
  "date": "2026-09-07",
  "payouts": [
    { "id": "payout-example-1", "providerId": "uber", "amount": 1000, "memo": "" }
  ]
}
```

上記は架空の形式例である。`providerId` はプラットフォームの ID、空文字は「未分類」を表す。プラットフォームを非表示にしても、既存の振込の集計対象からは外さない。`amount` は有限かつ正の数のみを採用する。`id` が欠けた入力や重複 ID には決定的な ID を補い、読込のたびに ID が変わらないようにする。

旧形式の `sourceData.transferAmount` は、`payouts` フィールドがない場合に限り、ID `legacy-transfer` の未分類の振込として読み込む。旧形式の有効な金額は丸めずに保持する。`sourceData` の元の値は残しても二重加算しない。`payouts: []` は明示的に振込がない状態として扱うため、削除した旧形式の振込が次の読込で復活することはない。不正な `payouts` フィールドも旧形式へのフォールバックには使わない。

`public/payout-data.js` の `normalize(record)` が日別の振込を正規化し、`summarize(records)` が振込合計・件数・プラットフォーム別合計・日付降順の明細を返す。日・週・月・年の対象日付の選択は呼び出し側で行う。集計は対象期間内の振込日を基準にする。

## 保存・バックアップ・ロールバック

正本は引き続き端末ごとの `localStorage` に置く。振込は日別記録の一部なので、JSON エクスポート／インポート、端末内の控え・復元ポイント、任意で有効にしたクラウド同期のスナップショットに既存の記録と一緒に含まれる。クラウド同期は既定で停止しており、この機能で有効にはならない。

旧形式のバックアップも読み込める。振込を含む記録を編集するときは、`schemaVersion: 3` に対応した版を使用する。古い版は新しい `payouts` を表示・集計できず、日別記録の正規化・編集保存によって追加フィールドを失う可能性がある。

旧版へ戻す前に、設定から全データの JSON バックアップを書き出して保管する。旧版では振込記録の編集を避ける。再び対応版へ戻したら、必要に応じて退避したバックアップを読み込み、振込の件数と合計を確認する。クラウド同期を利用している場合は、旧版の編集で対応版の記録を上書きしないよう、ロールバック中は同期を停止する。
